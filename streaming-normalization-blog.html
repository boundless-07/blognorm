One table too many rows: normalizing a streaming platform database

What happens when a Netflix- or YouTube-style service stores everything in a single watch-history table, and how normal forms fix it.

A streaming platform tracks people, plans, videos, creators, genres and every minute anyone watches. It is tempting to dump all of that into one wide table because it is easy to query at first. This post shows why that choice becomes expensive, and walks step by step to a clean design. The examples use a simplified model that applies equally to Netflix (studios and titles) or YouTube (channels and videos).

1. Entities and relationships

Start with the real-world things the platform cares about, before thinking about tables.

UserA person with an account, name and email.
PlanA subscription tier with a name and monthly price.
CreatorA studio or channel that publishes videos.
VideoA title with a duration, owned by one creator.
GenreA category such as Drama or Sci-Fi.
Watch eventA user watching a video at a point in time.

The relationships between them:

  • A plan has many users; each user is on one plan (1 : N).
  • A creator publishes many videos; each video has one creator (1 : N).
  • A video can have many genres and a genre covers many videos (M : N).
  • Users and videos are linked many-to-many through watch events (M : N), and each event carries its own data such as seconds watched.

2. The redundant design

The all-in-one version is a single table, WATCH_LOG, with one row per viewing:

WATCH_LOG(user_id, user_name, user_email, plan_id, plan_name, plan_price,
          video_id, title, duration_min, genres,
          creator_id, creator_name, watched_at, seconds_watched)

The candidate key is (user_id, video_id, watched_at). Here is what some rows look like:

The highlighted cells are repeated facts. A user's name is stored once per viewing, and a video's title and creator are stored once per viewer per viewing. On a real platform with billions of watch events, that is a large amount of wasted storage and, worse, many chances for the copies to disagree.

3. Anomalies it causes

Update anomaly

Nova Studios renames itself to Nova Pictures. Every row for every video it owns must change. If a job updates only some rows, the table now says the same creator has two names, and no query can tell which is right.

Insertion anomaly

A creator uploads a new video that nobody has watched yet. There is no row to put it in, because a row needs a user_id and watched_at to exist. Likewise a new user who has not watched anything cannot be recorded, and a new plan cannot be added until someone subscribes.

Deletion anomaly

Ben is the only viewer of a niche video and deletes his watch history. That row disappears, and the video's title, duration and creator vanish with it, even though the video still exists on the platform.

Other costs

Beyond the three classic anomalies, the genres column holds a list in one cell (Sci-Fi, Thriller), so finding all Thriller videos needs fragile text matching. Storage also grows with views rather than with content, which is the wrong thing to scale with.

4. Functional dependencies

A functional dependency X → Y means that a value of X always determines exactly one value of Y. Reading the business rules gives us:

FD1 user_id → user_name, user_email, plan_id FD2 plan_id → plan_name, plan_price FD3 video_id → title, duration_min, creator_id FD4 creator_id → creator_name FD5 video_id →→ genre (multi-valued: one video, many genres) FD6 (user_id, video_id, watched_at) → seconds_watched

Only FD6 depends on the whole key. Everything else depends on part of the key or on a non-key column, which is exactly where the redundancy comes from.

5. Applying the normal forms

First normal form (1NF): atomic values

Rule: every cell holds a single value, and there are no repeating groups.

Violation: genres stores Sci-Fi, Thriller in one cell (FD5).

Fix: store one genre per row, which is cleaner as its own table VIDEO_GENRE(video_id, genre_id) once we get to the end. After this step, the key of the main table is still (user_id, video_id, watched_at).

Second normal form (2NF): no partial dependencies

Rule: be in 1NF, and every non-key attribute must depend on the whole composite key.

Violations: user attributes depend only on user_id (FD1), and video attributes depend only on video_id (FD3). Each is a piece of the key, not the whole.

Fix: split the table into three:

USER(user_id, user_name, user_email, plan_id, plan_name, plan_price)
VIDEO(video_id, title, duration_min, creator_id, creator_name)
WATCH(user_id, video_id, watched_at, seconds_watched)

Now a user's name is stored once, and a video's title is stored once. But two problems remain inside USER and VIDEO.

Third normal form (3NF): no transitive dependencies

Rule: be in 2NF, and no non-key attribute may depend on another non-key attribute.

Violations:

  • In USER: user_id → plan_id → plan_name, plan_price. Price is really a fact about the plan.
  • In VIDEO: video_id → creator_id → creator_name. The name is really a fact about the creator.

Fix: move each transitive fact to a table of its own, keeping the key as a foreign key:

PLAN(plan_id, plan_name, plan_price)
CREATOR(creator_id, creator_name)
USER(user_id, user_name, user_email, plan_id FK)
VIDEO(video_id, title, duration_min, creator_id FK)

With this split, renaming a creator or changing a plan price is a one-row update, and a plan or creator can exist before it has any users or videos.

Boyce-Codd normal form (BCNF)

Rule: for every functional dependency X → Y, X must be a superkey.

Checking each table: in PLAN, CREATOR, USER and VIDEO the only determinant is the primary key. In WATCH the only determinant is the full composite key. VIDEO_GENRE has no non-key columns at all. Every determinant is a key, so the design is already in BCNF.

One note on emails: if user_email must be unique, it is a second candidate key of USER, which still satisfies BCNF because the dependency user_email → user_id has a key on its left side.

6. The normalized design

PLANplan_id (PK), plan_name, monthly_price
USER_ACCOUNTuser_id (PK), user_name, email (unique), plan_id (FK)
CREATORcreator_id (PK), creator_name
VIDEOvideo_id (PK), title, duration_min, creator_id (FK)
GENREgenre_id (PK), genre_name
VIDEO_GENREvideo_id (FK), genre_id (FK), composite PK
WATCH_EVENTuser_id (FK), video_id (FK), watched_at, seconds_watched; composite PK

As SQL:

CREATE TABLE plan (
  plan_id INT PRIMARY KEY,
  plan_name VARCHAR(40) NOT NULL,
  monthly_price DECIMAL(8,2) NOT NULL
);
CREATE TABLE user_account (
  user_id INT PRIMARY KEY,
  user_name VARCHAR(80) NOT NULL,
  email VARCHAR(120) UNIQUE NOT NULL,
  plan_id INT NOT NULL REFERENCES plan(plan_id)
);
CREATE TABLE creator (
  creator_id INT PRIMARY KEY,
  creator_name VARCHAR(80) NOT NULL
);
CREATE TABLE video (
  video_id INT PRIMARY KEY,
  title VARCHAR(120) NOT NULL,
  duration_min INT NOT NULL,
  creator_id INT NOT NULL REFERENCES creator(creator_id)
);
CREATE TABLE genre (
  genre_id INT PRIMARY KEY,
  genre_name VARCHAR(40) UNIQUE NOT NULL
);
CREATE TABLE video_genre (
  video_id INT REFERENCES video(video_id),
  genre_id INT REFERENCES genre(genre_id),
  PRIMARY KEY (video_id, genre_id)
);
CREATE TABLE watch_event (
  user_id INT REFERENCES user_account(user_id),
  video_id INT REFERENCES video(video_id),
  watched_at TIMESTAMP,
  seconds_watched INT NOT NULL,
  PRIMARY KEY (user_id, video_id, watched_at)
);

To rebuild the original wide view, join the tables back together:

SELECT u.user_name, p.plan_name, v.title, c.creator_name, w.seconds_watched
FROM watch_event w
JOIN user_account u ON u.user_id = w.user_id
JOIN plan p         ON p.plan_id = u.plan_id
JOIN video v        ON v.video_id = w.video_id
JOIN creator c      ON c.creator_id = v.creator_id;

7. Trade-offs and takeaways

Normalization is not free. Queries need more joins, and at the scale of a real streaming service some read-heavy paths, such as a home-page recommendation feed, are often deliberately denormalized into caches or analytics stores for speed. The key point is that this is done on purpose, as a copy derived from a clean source of truth, rather than by accident in the core transactional database.

  • Identify entities and relationships first, then derive functional dependencies from real business rules.
  • Redundancy shows up as update, insertion and deletion anomalies.
  • 1NF removes repeating values, 2NF removes partial dependencies, 3NF removes transitive ones, and BCNF makes sure every determinant is a key.
  • The result here is seven small, well-keyed tables where each fact is stored in exactly one place.
