Normalizing the Cart

How a marketplace like Amazon or Flipkart should split its data into tables, and what breaks when it does not.

Topic: functional dependencies, 1NF to BCNFAbout 9 minute read

Every time you place an order, a shop has to remember who you are, what you bought, who sold it, what it cost and where it is going. The question is where each of those facts is written down. If the same fact lives in many places, the places will eventually disagree. Normalization is the discipline of making sure each fact is stored once, in the one place that owns it.

This post walks through the whole exercise on a marketplace order system: find the entities, write down the functional dependencies, spot the redundancy and the anomalies it causes, then rebuild the schema in third normal form.

1. Start with the entities

An entity is a thing the business keeps records about. Reading the checkout flow of a marketplace gives a short list.

  • CustomerPerson with an account, email and phone.
  • AddressA delivery address. One customer has several.
  • CategoryElectronics, Home, Books. Can be nested.
  • ProductThe item in the catalogue, such as a particular earbud model.
  • SellerA business that sells on the platform.
  • ListingOne seller's offer for one product, with its own price and stock.
  • OrderA purchase placed by a customer on a date.
  • Order itemOne line of an order: which listing, how many, at what price.
  • PaymentHow and when an order was paid.

Shipments and reviews are further entities in the real systems. They follow the same pattern, so this post leaves them out.

2. The table everyone builds first

A common first attempt is to put everything about an order on one row. It looks convenient because one query returns everything the order page needs. Here is a trimmed version, called order_flat, with the primary key (order_id, product_id, seller_id).

3. Functional dependencies

A functional dependency A → B means that if you know A, there is exactly one possible B. These come from business rules, not from the data that happens to be in the table today. For the table above, the rules are:

order_id → customer_id, order_date customer_id → customer_name, city product_id → product_name, category seller_id → seller_name (order_id, product_id, seller_id) → qty, unit_price

Only the last line depends on the whole key. Everything else depends on a part of the key or on another non-key column. That mismatch is exactly what normal forms measure.

Assumption to revisitThe flat table treats product_id → seller_id as true, meaning one seller per product. On Amazon and Flipkart the same product is sold by many sellers at different prices, so that dependency does not hold in the real system. We fix this with a listing table in section 5.

4. What goes wrong: anomalies

Update anomaly

Asha Rao moves from Pune to Bengaluru. Her city is stored on every order row she ever placed, so the update has to touch all of them. If a script misses one, the database now says she lives in two cities. The earbuds in the table already show the same problem: the product name was edited in some rows and not others, so a search for "boAt" finds one order and misses the other.

Insert anomaly

A new seller registers and lists a product. With this table you cannot record the product or the seller until somebody orders it, because order_id is part of the primary key and cannot be empty. The catalogue cannot exist without orders.

Delete anomaly

Order 1003 is cancelled and its row is deleted. It was the only row mentioning product P31 and seller S9, so the water bottle and HomeKart vanish from the system along with the order.

Other costs of redundancy

  • Wasted storage. A customer's name and address repeat on every line of every order. For millions of orders this is large, and it also slows scans.
  • Inconsistent values. "Electronics", "electronics" and "Electronic" become three categories in reports.
  • Hard-to-trust analytics. Revenue by seller depends on which spelling of the seller name each row happens to carry.

5. Normalizing step by step

First normal form (1NF): atomic values, no repeating groups

Each cell holds one value. A design that stores items = "P10, P22" in one cell, or phone1, phone2, phone3 as columns, breaks 1NF. You cannot join, count or index a list hidden in a text cell. The flat table above already has one product per row, so it satisfies 1NF. Customer phone numbers would move to a child table if a customer may have several.

Second normal form (2NF): no partial dependencies

The table must be in 1NF, and every non-key column must depend on the whole primary key. With the composite key (order_id, product_id, seller_id), three groups fail:

  • customer_id, customer_name, city and order_date depend on order_id alone.
  • product_name and category depend on product_id alone.
  • seller_name depends on seller_id alone.

Move each group to its own table keyed by the part it depends on. That leaves order_items(order_id, product_id, seller_id, qty, unit_price) holding only what depends on the full key.

Third normal form (3NF): no transitive dependencies

The table must be in 2NF, and no non-key column may depend on another non-key column. One chain remains:

  • order_id → customer_id → customer_name, city: customer details belong in customers.
  • product_id → product_name, category and seller_id → seller_name: product and seller details belong in their respective tables.

Boyce-Codd normal form (BCNF)

BCNF is stricter: for every dependency A → B, A must be a candidate key. In the schema below every determinant is a key, so it is also in BCNF. BCNF violations usually appear only when a table has several overlapping candidate keys, which is rare in a design like this.

6. The normalized schema

1 means one, N means many. PK is the primary key and FK is a foreign key. Each line reads from the "1" side to the "N" side, for example one customer places many orders.

CREATE TABLE customers (
  customer_id  BIGINT PRIMARY KEY,
  name         TEXT NOT NULL,
  email        TEXT NOT NULL UNIQUE,
  phone        TEXT
);

CREATE TABLE addresses (
  address_id   BIGINT PRIMARY KEY,
  customer_id  BIGINT NOT NULL REFERENCES customers,
  line1        TEXT NOT NULL,
  city         TEXT NOT NULL,
  state        TEXT NOT NULL,
  pincode      CHAR(6) NOT NULL
);

CREATE TABLE categories (
  category_id  INT PRIMARY KEY,
  name         TEXT NOT NULL UNIQUE,
  parent_id    INT REFERENCES categories
);

CREATE TABLE products (
  product_id   BIGINT PRIMARY KEY,
  name         TEXT NOT NULL,
  category_id  INT NOT NULL REFERENCES categories
);

CREATE TABLE sellers (
  seller_id    BIGINT PRIMARY KEY,
  name         TEXT NOT NULL
);

-- One seller's offer for one product: same product, many sellers
CREATE TABLE listings (
  listing_id   BIGINT PRIMARY KEY,
  product_id   BIGINT NOT NULL REFERENCES products,
  seller_id    BIGINT NOT NULL REFERENCES sellers,
  price        NUMERIC(10,2) NOT NULL,   -- current price
  stock        INT NOT NULL CHECK (stock >= 0),
  UNIQUE (product_id, seller_id)
);

CREATE TABLE orders (
  order_id     BIGINT PRIMARY KEY,
  customer_id  BIGINT NOT NULL REFERENCES customers,
  address_id   BIGINT NOT NULL REFERENCES addresses,
  ordered_at   TIMESTAMPTZ NOT NULL,
  status       TEXT NOT NULL
);

CREATE TABLE order_items (
  order_id     BIGINT REFERENCES orders,
  listing_id   BIGINT REFERENCES listings,
  quantity     INT NOT NULL CHECK (quantity > 0),
  unit_price   NUMERIC(10,2) NOT NULL,   -- price paid at order time
  PRIMARY KEY (order_id, listing_id)
);

CREATE TABLE payments (
  payment_id   BIGINT PRIMARY KEY,
  order_id     BIGINT NOT NULL REFERENCES orders,
  method       TEXT NOT NULL,
  amount       NUMERIC(10,2) NOT NULL,
  status       TEXT NOT NULL
);
Why unit_price appears twicelistings.price is today's price and changes. order_items.unit_price is a historical fact: what this customer paid on that day. They answer different questions, so storing both is not redundancy. Dropping the second column would silently rewrite old invoices every time a seller changed a price. The same thinking applies to the shipping address, which in production is often copied into the order or made immutable so that editing an address does not alter past orders.

7. Why it improves consistency, and what it costs

With the normalized schema, each fact has one home. A customer's new city, a renamed product or a corrected category is a single-row update that every order and report sees at once. Foreign keys, UNIQUE and CHECK constraints make the database reject bad data itself, and a product can be added, or an order cancelled, without losing anything else.

The cost is joins: rebuilding an order page touches orders, items, listings, products, sellers and addresses. Large marketplaces handle this by copying data on purpose, for example into a search index or an order-history view. Those copies are generated from the normalized tables, which stay as the source of truth. Normalize first, then denormalize only where measurements show a real read bottleneck.
